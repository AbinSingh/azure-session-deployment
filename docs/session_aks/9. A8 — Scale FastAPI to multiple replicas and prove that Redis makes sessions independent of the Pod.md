# Big picture

Currently:

    Internet
       │
       ▼
    LoadBalancer
       │
       ▼
    Service
       │
       ▼
    FastAPI Pod 1
       │
       ▼
    Azure Managed Redis

We'll change it to:

                             ┌── FastAPI Pod 1 ──┐
                             │                   │
    Internet → LoadBalancer → Service           ├──→ Azure Managed Redis
                             │                   │
                             └── FastAPI Pod 2 ──┘

The key point:

The session belongs in Redis, not in the FastAPI Pod.

So if:

    Login → Pod 1
    /profile → Pod 2

the session should still work.

# A8.4 — The interesting experiment

Now we want to know: Which Pod actually handled each request?

If your application doesn't currently expose that information, let's add a temporary debugging endpoint.

Add this to your FastAPI application:

    @app.get("/debug/pod")
    def debug_pod(request: Request):
        return {
            "hostname": socket.gethostname(),
            "pod_name": os.getenv("HOSTNAME"),
            "client": request.client.host if request.client else None,
        }

The important value is:

HOSTNAME Kubernetes automatically sets the container hostname to the Pod hostname.

# A8.8 — Make the test deterministic

Rather than relying on the LoadBalancer to randomly switch Pods, we'll directly access each Pod
through kubectl port-forward.

This is purely a learning/debugging technique.

Find the Pod names:

kubectl get pods -n session-app

Suppose:

    POD1 = session-api-xxxxx-aaaaa
    POD2 = session-api-xxxxx-bbbbb

# Open PowerShell window 1:

    kubectl port-forward -n session-app pod/session-api-7f585ddd75-g6svn 8001:8000

    You'll get:

# Open PowerShell window 2:

kubectl port-forward -n session-app pod/session-api-7f585ddd75-mc7rv 8002:8000

Now:

localhost:8001 → Pod 1
localhost:8002 → Pod 2

# A8.11 — Compare this with the old in-memory architecture

Previously:
    
                     ┌── Pod 1
                     │    │
                     │    └── Python dictionary
                     │
    Load Balancer ───┤
                     │
                     └── Pod 2
                          │
                          └── Python dictionary

There are two completely independent dictionaries:

    Pod 1 dictionary ≠ Pod 2 dictionary

    Therefore:
    
        Login → Pod 1
        /profile → Pod 2
        
    could fail.

# With Redis:

                     ┌── Pod 1 ──┐
                     │           │
    Load Balancer ───┤           ├── Azure Redis
                     │           │
                     └── Pod 2 ──┘

Both Pods use:

        ONE shared session store

That's the fundamental reason we moved the session state out of Python memory.

# A8.12 — Now test through the real LoadBalancer

Close the two port-forward sessions with: Ctrl + C

Then access: http://<PUBLIC-IP>/docs

Call: POST /login

Then: GET /profile

Repeat /profile several times.

You don't necessarily know which Pod handles each request, but both Pods can access the same Redis session.

# A8.15 — This is the key lesson

We now have three different kinds of state:

1. Pod state

Ephemeral:

    Pod
     └── process memory

Can disappear at any time.

2. Container/image

Immutable application artifact:

    ACR
     └── session-api:a8

3. Session state

Shared/persistent application state:

    Azure Managed Redis
     └── session_id → user session

The architecture is therefore:

             Stateless application
          ┌──────────────────────────┐
          │                          │
          ▼                          ▼
       Pod 1                      Pod 2
          │                          │
          └──────────┬───────────────┘
                     │
                     ▼
             Stateful external
                  service
                     │
                     ▼
             Azure Managed Redis

This is the architectural pattern we're trying to learn.

               \             /
                \           /
                 ▼         ▼
              Azure Managed
                  Redis
                    │
                    ▼
              Session State

And there's a very important consequence:

Kubernetes can freely create, destroy, restart, and move FastAPI Pods without destroying user sessions, because the sessions don't live inside the Pods.
